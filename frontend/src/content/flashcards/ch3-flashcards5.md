# <span style="color: rgb(var(--brand));">TCP 协议</span>

### 前面把“可靠传输”的底层原理铺好了，这一节的主角 TCP（传输控制协议）就是把这些原理真正落地的那个家伙。它是因特网里最讲究、最可靠的运输层协议，Web、邮件、文件传输都靠它。一句话：`TCP 就是那个“绝对不会把你信件搞丢”的可靠邮差`。

# <span style="color: rgb(var(--brand-dark));"> 3.5.1 TCP 是什么 </span>

### TCP被称为是`面向连接的（connection-oriented）`,这是因为在一个应用进程可以开始向另一个进程发送数据之前，两个进程必须先握手，即它们必须发送某些预备报文段。就好像你要约女孩出去吃饭一样，date前总得约定好地点，总不能给人家直接拽到约会地点吧。作为TCP连接建立的一部分，连接的双方都将初始化许多与TCP连接相关的状态变量。而TCP“连接”并不像像你想的那样，好像是有一条线连在两个主机进程中，而是逻辑连接，其共同状态仅仅保留在通信端系统的TCP程序中。由于TCP进运行在端系统中，所以中间的网络元素不会维持TCP连接状态。一句话，中间路由器管你这那的，人家看到的就只有数据报而已，对连接完全视而不见。TCP提供的是`全双工服务(full-duplex service)`如果主机A与主机B存在一条TCP连接，那么应用层数据就可以从A流向B，也可以从B流向A，双向奔赴了属于是。而且重要的是，TCP连接还是“纯爱战士”，总是`点对点(point-to-point)`的。

# <span style="color: rgb(var(--brand-dark));"> 3.5.2 TCP 报文段结构 </span>

### TCP 报文段的首部（20 字节起）比 UDP 复杂得多，但核心就几个字段：

* ### `源端口号 / 目的端口号`：还是那对“门牌号”，做多路复用/分解。另外，同UDP一样，TCP首部也包括检验和字段
* ### `序号（Sequence Number）`：32比特，本报文段首字节在字节流中的位置。
* ### `确认号（ACK Number）`：32比特，期望收到的下一个字节的序号（即“我已经收到你前面所有字节”）。
* ### `接收窗口字段（receive window field）`：该字段用于流量控制，用于指示接收方愿意接受的字节数量。
* ### `首部长度字段（header length field）`：4比特，用于指出 TCP 报文段的首部有多长，从而明确 TCP 报文段中的实际数据（Payload）从哪里开始。
* ### `选项字段（options field）`：用于发送方和接收方协商最大报文长度，或在告诉网络环境下作窗口调节因子时使用
* ### `标志字段（flag field）`：6比特，ACK比特用于确认字段中的值是有效的，包括一个对已被成功接收报文段的确认。RST、SYN和FIN用于连接的建立和拆除。还有PSH和URG，感兴趣可以自己查一查就不都讲了（其实是我也不太了解了）。

 

# <span style="color: rgb(var(--brand-dark));"> 3.5.3 三次握手：建立连接 </span>

### TCP 建立连接靠的是经典的“`三次握手`”：

</div>

> ① 客户端 → 服务器：`SYN`（我想连你，这是我的初始序号 x）
> ② 服务器 → 客户端：`SYN + ACK`（好，我确认，这是我的初始序号 y）
> ③ 客户端 → 服务器：`ACK`（收到，连接建立）

### 为什么是三次而不是两次？因为要`双方都确认对方能收发`，防止历史连接请求造成混乱。三次之后，双方各自分配好缓冲区，开始传数据。

# <span style="color: rgb(var(--brand-dark));"> 3.5.4 超时估计 & 流量控制 </span>

### 前面 rdt3.0 提到了超时重传，但“超时”设多长才合适？设短了会误重传，设长了又反应慢。TCP 通过`往返时间估计`动态调整：

> `EstimatedRTT = (1-α)·EstimatedRTT + α·SampleRTT`（指数加权移动平均）
> 超时时间 `TimeoutInterval` 还要留出安全余量，随 RTT 波动而变。

### 还有`流量控制（Flow Control）`：防止发送方把接收方的缓冲区“灌爆”。接收方在每个报文段里都带上自己的“接收窗口（rwnd）”，告诉发送方“我现在还能吃下多少字节”，发送方就照着这个量发。

# <span style="color: rgb(var(--brand-dark));"> 3.5.5 可靠数据传输 </span>

### 前面说过，因特网的网络层服务是“摆烂”的，是不可靠的，既不保证数据报的交付，不保证数据报的按序交付，也不保证数据报的完整性。TCP在IP的不可靠的尽力而为的服务上创建了一种可靠数据传输服务。TCP的可靠数据传输服务确保其从接收缓存中读出来的数据流是无损坏，无间隙，非冗余和按序的数据流；即该字节流和从里一个端系统发出的字节流完全相同。

> 上图给出了一个TCP发送方高度简化的描述。我们可以看到在TCP的发送方有三个与发送和重传有关的主要事件：从上层应用接收数据；定时器超时和收到ACK。TCP从应用程序接收数据，将数据封装到一个报文段当中，并把报文段传给IP。注意到每个报文段都包含一个序号，这个序号就是该报文段第一个数据字节的字节流编号。如果定时器没有为其它的报文段运行，泽当报文段传给IP时，TCP启动该定时器。定时器的过期间隔时`TimeoutInterval`。
> 第二个主要的事件是超时。TCP通过重传引起超时的报文段来响应超时事件。然后TCP重启定时器。
> 第三个主要的事件是处理一个来自接收方发送的确认报文段ACK，通过接收到ACK来判断要不要重传。

### 值得注意的是，编号方式可能跟大部分人原先设想的不同，TCP报文段的序号并不是连着的，是按字节流号进行编排的。比如说初始序号ISN=1000，包的SEQ=1001一个报文段传了300个字节，那么下一个报文段的序列号就是1301，以此类推。

# <span style="color: rgb(var(--brand-dark));"> 3.5.6 流量控制 </span>

### 流量控制说白了就是在建立TCP连接的双方维护一个可以动态调整的窗口来缓存报文段。举个例子，你每天上课学习的时间是有限的，老师要是一天讲二十个小时，换谁来都听不进去，脑袋的“缓存”是有限的，你一天就能消化两个小时学习的知识，剩下的只能扔掉了，这就是UDP的原理，并不提供流量控制服务。而TCP就比较聪明了，会和老师协商：“老师啊，咱一天讲两个点中不呢？”完了老师说：“中。”就这样，两者之间实现了流量控制，双方都能完整的接收到对方的反馈。
