# <span style="color: rgb(var(--brand-dark));"> 2.3 HTTP概述 </span>

### Web的应用层协议是超文本传输协议（来跟我念一遍 ：HyperText Transfer Protocol，HTTP），它是Web的核心。HTTP由两个程序实现：一个客户程序一个服务器程序。客户程序和服务器程序运行在不同的端系统中，通过交换HTTP报文进行会话。HTTP定义了这些报文的格式以及客户和服务器交换报文交换的方式。为了让你能够在接下来舒舒服服的学习，我们先来回顾一些Web的术语。

### Web页面是由对象组成的，（人家Web页面最不缺的就是对象，对说你呢）。一个对象（object）只是一个文件，诸如一个HTML文档，一个JPEG图片，一个MP4的视频，它们可以通过一个URL寻址。在HTML页面中通过对象的URL引用页面中的其他对象：如果一个Web页面包含一个HTML文档和5张JPEG图形，那么这个Web页面就有6个对象。每个URL有两部分组成：存放对象的服务器主机名和对象的路径名。比如，URL http://www.someSchool.edu/somePlace/pic.gif 其中的`www.someSchool.edu`就是主机名,`somePlace/pic.gif`就是文件路径。Web浏览器实现了HTTP的客户端，Web服务器实现了HTTP的服务器端，它用于储存web对象，每个对象由URL寻址。URL就跟你家门牌号一样，Web通过门牌号找到你家然后把你给请出来。流行的Web服务器由Apache和Microsoft Internet Information Server。

## <span style="color: rgb(var(--brand-dark));"> 2.3.1 HTTPS概述 </span>

### 好了，现在终于可以揭晓开头埋下的那个问题了——https:// 里的这个“s”到底是什么？它的全称是安全套接字层/传输层安全协议（SSL/TLS），这里的“s”代表 Secure（安全）。普通的 HTTP 是明文传输的，你发出的每一个请求、账号、密码，都像一张明信片一样在网络里“裸奔”，任何一个“路过”的人都可能偷瞄一眼。而 HTTPS 就是给这张明信片套上了一个保险箱——它在 HTTP 和 TCP 之间加了一层 TLS 加密层。

### HTTPS 具体做了三件大事：加密（把明文变成密文，别人偷看了也看不懂）、完整性校验（防止数据在传输途中被人偷偷篡改）、身份认证（确认你连的真的是正牌服务器，而不是一个冒充的钓鱼网站）。它的加密思路是“组合拳”：先用非对称加密（公钥/私钥）安全地交换一把临时钥匙，再用这把钥匙做对称加密去快速加密后面海量的数据，既安全又高效。至于服务器要怎么证明“我是真的我”，靠的是数字证书（certificate），由受信任的证书颁发机构（CA）给它背书，浏览器一看证书就知道可以放心交易了。HTTPS 默认使用的端口也从 HTTP 的 80 换成了 443。

## <span style="color: rgb(var(--brand-dark));"> 2.3.2 非持续连接与持续连接 </span>

### 说完了 HTTP 是什么、HTTPS 又是什么，接下来看看 HTTP 到底是怎么“运输”数据的。前面说过 HTTP 建立在 TCP 之上，而连接的使用方式有两种：非持续连接和持续连接。

1. **非持续连接（non-persistent connection）**：每个请求/响应对都用一条全新的 TCP 连接，传完一个对象就立刻关闭。比如一个页面里有 1 个 HTML 和 10 张图片，就得依次建立 11 条 TCP 连接。HTTP/1.0 时代就是这种“一锤子买卖”的模式，效率低得可怜。
2. 持续连接（persistent connection）：同一条 TCP 连接上可以连续传输多个对象，传完一个不急着关，接着传下一个。HTTP/1.1 默认采用这种方式，就像打一次电话把十件事一口气说完，而不是每说一句就挂断重拨。

### 衡量这种开销的“时间单位”叫往返时间（Round-Trip Time，RTT），就是一个分组从客户端跑到服务器再跑回来所花的时间。用非持续连接请求一个对象，光建立 TCP 连接这一下就要多花 2 个 RTT，而持续连接能把这份开销摊薄到一连串对象上。再配合流水线（pipelining）技术，还能不等上一个请求的响应回来就连续发出多个请求，速度直接起飞。

# <span style="color: rgb(var(--brand-dark));"> 2.3.3 HTTP报文格式 </span>

### 最后，让我们近距离看看 HTTP 的“信”到底长什么样。HTTP 报文分两种：请求报文（request message）和响应报文（response message），而且它们都是 ASCII 文本，人眼直接就能看懂。

### 请求报文由三部分组成：

1. 请求行（request line）：包含方法（method）、URL 和 HTTP 版本。常见的方法有：GET（索取对象）、POST（提交表单，把用户输入填进实体体）、PUT（上传对象）、DELETE（删除对象）、HEAD（只取首部不取实体，相当于“只看看不下载”）。
2. 首部行（header lines）：一行一个“字段名：值”，比如 Host（访问哪台主机）、Connection（要不要持续连接）、User-Agent（我用的是什么浏览器）。
3. 实体体（entity body）：GET 请求一般是空的；POST 请求时，你在网页表单里填的那些数据就装在这里。

### 响应报文同样由三部分组成：

1. 状态行（status line）：HTTP 版本 + 状态码 + 状态描述。状态码是你最该记住的“暗号”：200 OK（请求成功，对象在这）、301 Moved Permanently（对象搬家了，去新地址找它）、400 Bad Request（你发的请求有问题，服务器看不懂）、404 Not Found（你要的对象不存在，传说中的“404 页面”）、500 Internal Server Error（服务器自己内部炸了，锅不在你）。
2. 首部行：比如 Content-Type（返回的是 HTML 还是图片）、Content-Length（实体有多长）、Set-Cookie（先卖个关子，下一张卡细说）。
3. 实体体：真正的“货物”——那个 HTML 文件、那张图片。
