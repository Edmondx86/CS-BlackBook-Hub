# <span style="color: rgb(var(--brand-dark));"> 2.4 HTTP是无状态的 </span>

### HTTP是无状态的，HTTP是无状态的，HTTP是无状态的。HTTP使用TCP作为它的支撑协议，而不是UDP。客户首先发起一个和服务器TCP连接，连接建立之后客户和服务器进程就可以通过套接字socket来访问TCP。服务器再给客户发送请求的资源的时候，并不保存客户的状态信息，所以当一个客户在短时间内发送多次请求时，不会因为发送了请求的资源后就不再响应，而是一致重新发送该对象。就好像你刚请求了对象A，然后你跟Web服务器说：喂，给我刚才的对象。然后服务器会说：啥？什么对象啊？你再说：刚才的A！服务器：A什么啊？只有当你说了：给我对象A之后，服务器才知道：哦你要对象A啊。Web服务器总是打开的，具有一个固定的IP地址，而它服务于数以万计的不同浏览器的请求。

## <span style="color: rgb(var(--brand-dark));"> 2.4.1 Cookie：给无状态的 HTTP 发一张会员卡 </span>

### 既然 HTTP 是个“七秒记忆”的失忆症患者，那网站是怎么做到“记住你登录过”“记住你购物车里加了啥”的呢？答案就是 Cookie（小甜饼）。它其实不是单一的一个东西，而是由四个组件协作的一套机制：

1. `响应报文里的 Set-Cookie 首部行`：你第一次访问某网站时，服务器在响应里塞进一行 Set-Cookie：1678，相当于给你发了一个独一无二的编号。
2. `请求报文里的 Cookie 首部行`：你的浏览器收到后，把这个编号老老实实记在本地的一个 cookie 文件里，之后每次再访问同一网站，都会自动在请求里带上 Cookie：1678，等于自报家门。
3. `浏览器端保存的 cookie 文件`：就存在你的电脑上，是一堆“站点名 + 编号”的小本本。
4. `网站后台的数据库`：服务器拿着你报上来的编号去数据库里一查，就能把你所有的历史记录、购物车、偏好统统翻出来。

### 打个比方：你第一次去一家“网络杂货铺”，老板递给你一张会员卡（Set-Cookie），上面写着一个会员号；你把卡揣进兜里（浏览器保存 cookie），下次再来进门就亮一下卡（请求里带上 Cookie），老板一扫会员号，就知道“哦，老顾客又来了”。有了这套机制，无状态的 HTTP 就“借尸还魂”般地拥有了记忆。当然，Cookie 也不是没有争议——你的浏览记录被记录在案，隐私问题随之而来，所以现在浏览器都给了你“清除 Cookie”“无痕模式”这些开关，把“记不记”的选择权还给你。

## <span style="color: rgb(var(--brand-dark));"> 2.4.2 Web缓存（代理服务器） </span>

### 讲完了“记忆”，再讲“加速”。想象一下：全校几万师生都去访问同一个教学网站，如果每次请求都千里迢迢跑到远端服务器，一来一回又慢又占带宽。聪明的做法是在校园里放一个“中间人”——`Web 缓存器（Web cache）`，也叫代理服务器（proxy server）。它会保存最近请求过的对象副本：当有人来要某个对象时，如果缓存里正好有这个对象（缓存命中），就直接返回，压根不用出校园网；如果没有（缓存未命中），代理就自己出面去向真正的源服务器把对象取回来，存一份副本，再转发给请求者，下一个要同样东西的人就捡现成了。

### 用好 Web 缓存有三大好处：一是降低客户端的响应时间（数据就近取，不用每次跑长途）；二是大大减少机构接入链路的流量（重复请求被缓存“拦截”，不再挤爆那条连接到外网的窄路）；三是降低整个因特网的流量（大家都少往源服务器跑）。但缓存也有个致命问题：它存的副本可能是陈旧的——源服务器上的对象已经更新了，缓存里还躺着旧版本。怎么破？靠条件 GET（conditional GET）：缓存器向服务器请求时带上 If-Modified-Since 首部行，相当于问一句“这个对象在我存下之后改过吗”。没改过，服务器就只回一个 304 Not Modified（不带实体，省流量）；改过了，才把新对象完整发过来。

### 到这里，Web 这一环就完整了：HTTP 负责“说话”，HTTPS 负责“保密”，Cookie 负责“记住你”，Web 缓存负责“跑得快”。下一节，我们就把目光转向网络世界的“黄页电话本”——DNS，看看你敲下的域名是怎么被翻译成 IP 地址的。
