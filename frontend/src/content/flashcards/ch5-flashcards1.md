# <span style="color: rgb(var(--brand));">网络层控制平面概述</span>

### 上一章我们把数据平面翻了个底朝天：分组进路由器、查转发表、从合适的端口扔出去，完事。可你有没有停下来想过一个更根本的问题——**转发表里的每一项，究竟是谁算出来、又是谁填进去的？** 这就是本章的主角：控制平面（control plane）。如果说数据平面是“司机照着导航开车”，那控制平面就是“在后台帮全网司机规划路线的导航系统”。

### 说白了，网络层被硬生生劈成了两半：一半负责搬货，一半负责指路。这一节我们先把这两半的边界划清楚，再交代本章的地图。

# <span style="color: rgb(var(--brand-dark));">5.1.1 转发与路由选择：一对双胞胎</span>

### 这两个词长得像，中文也像，但千万别搞混，它们是理解整个第五章的第一道门槛：

* 转发（forwarding）：路由器收到分组，根据转发表把它送到正确的输出链路接口。这是一个<strong>本地、瞬时</strong>的动作，快到要在纳秒级完成，所以通常直接用硬件实现。
* 路由选择（routing）：网络中的路由器互相交换信息，算出从源到目的地该走哪条路，再把结果写进转发表。这是一个<strong>全局、相对慢</strong>的过程，通常由软件完成。

### 一句话：**转发是“查表”，路由选择是“算表”**。转发表就是连接这两件事的桥梁——控制平面负责算表，数据平面负责查表。把这句话刻在脑子里，后面所有的协议都只是它的不同实现方式。

# <span style="color: rgb(var(--brand-dark));">5.1.2 传统方式：每路由器控制</span>

### 历史最悠久、也最符合直觉的做法是：每台路由器都自己跑一套路由算法。它们和相邻路由器交换信息（“我离某个网络有 3 跳，你呢？”），然后各自独立地算出自己的转发表。

> 典型代表：OSPF、BGP 都属于这一类。

### 就像一群自驾游的车主，每人手里只有一张局部地图，靠互相打听来决定下一段路怎么开。好处是**分布式、健壮**——某台路由器挂了，其他路由器照样能自己算；代价是每台设备各自为政，很难从全局视角做出最优调度。

# <span style="color: rgb(var(--brand-dark));">5.1.3 现代方式：逻辑集中控制（SDN）</span>

### 既然“各自算”不够灵活，那就换一条路：把算表这件事从路由器里整个抽出来，交给一个远端（或一组）控制器（controller）统一计算，再由它把算好的转发表下发给每台路由器。路由器从此只转发、不算路，退化成一台听话的哑交换机。

### 就像把全城的红绿灯交给一个中央交通大脑统一调度，它看得见全城路况，能全局指挥；而每辆车（路由器）只管照着灯走。

### 注意“逻辑集中”这四个字：控制逻辑在物理上完全可以跑在多个服务器上（集群），但在逻辑视图里，它就像一个集中的大脑。这种“大脑 + 四肢”的架构，就是 5.5 节 SDN 的主角。

### 接下来的内容就沿着“算表”这条线一路展开：

1. 5.2 路由选择算法：不管哪种控制平面，底层都得有算最短路的算法——链路状态（Dijkstra）与距离向量（Bellman-Ford）。
2. 5.3 / 5.4 域内与域间路由：因特网太大，于是划成一个个自治系统（AS），AS 内部用 OSPF，AS 之间用 BGP。
3. 5.5 SDN 控制平面：逻辑集中控制的现代实现，核心是 OpenFlow。
4. 5.6 ICMP 协议：网络层的报信员——差错报告怎么发，`ping` 和 `traceroute` 又是怎么靠它工作的。
5. 5.7 网络管理：SNMP 与 NETCONF/YANG，看看这一大堆设备平时是怎么被照看的。

## 所以，控制平面就是网络层的“幕后大脑”：数据平面负责搬货，控制平面负责指路。搞懂它，你就真正明白了转发表背后那套来龙去脉。
