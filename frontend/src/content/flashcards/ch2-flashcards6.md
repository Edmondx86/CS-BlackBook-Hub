# <span style="color: rgb(var(--brand));">P2P 文件分发</span>

### 还记得第一张卡说过：C/S 架构最怕的就是“一台服务器扛不住所有客户”。这个问题在“分发大文件”时暴露得最彻底——比如某个热门电影、某个大型软件包，几百万人同时来下载，服务器带宽瞬间被吸干。P2P 架构给出了完全不同的答案：**下载的人越多，反而越快**。这听起来像“反常识”，但它正是 P2P 的核心魅力。

# <span style="color: rgb(var(--brand-dark));"> 2.7 C/S 与 P2P：分发时间大 PK </span>

### 先定义一下“分发时间”：就是“把一个文件从一台服务器送到 N 个对等方手里，最短需要多久”。我们假设文件大小是 F 比特，服务器上传速率是 `us`，每个对等方的上传速率是 `ui`，下载速率是 `di`。为了公平起见，先忽略一堆细节，只看核心结论。

### 先看 C/S 架构。服务器要把文件发给 N 个人，得上传 N 份；而且最慢的那个人（下载速率最小的 `dmin`）也拖后腿。所以分发时间大约是：

```
D_cs = max{ N·F/us , F/dmin }
```

### 注意 `N·F/us` 这一项：它随 N 线性增长！人多一倍，时间多一倍，服务器总有一天扛不住，这就是 C/S 的“天花板”。

### 再看 P2P 架构。每个对等方下载的同时，也在把自己拿到的部分“上传”给别的对等方，等于人人都是小服务器。分发时间是：

```
D_p2p = max{ F/us , F/dmin , N·F/(us + Σui) }
```

### 关键在第三项 `N·F/(us + Σui)`：分母里多了所有对等方的上传速率之和 `Σui`。人越多，`Σui` 越大，分母越大——所以这一项几乎不随 N 增长！这就是 P2P 的“可扩展性魔法”：来下载的人越多，贡献的上传能力也越多，大家互相喂，速度不但不掉，反而可能更快。难怪 BitTorrent 当年能风靡全球。

## <span style="color: rgb(var(--brand-dark));"> 2.7.1 BitTorrent：P2P 的明星应用 </span>

### P2P 文件分发最出名的实现就是 BitTorrent（BT）。它的玩法是这样的：

1. torrent 种子文件：你想下载某个大文件，得先拿到一个 `.torrent` 种子文件，里面记录了文件的信息和“追踪器（tracker）”的地址。
2. 追踪器（tracker）：一个“登记处”，记录着“当前谁在参与下载这个文件”。这些参与下载的对等方集合叫一个 `torrent`，也叫“群（swarm）”。
3. 对等方互相交换块：文件被切成很多小块（chunk），群里的对等方们“你有我没有”地互相交换，每个人既是下载者又是上传者。
4. 最稀缺优先（rarest-first）：新加入的对等方，优先去下载“整个群里最稀缺、拥有者最少”的那个块，尽快让这个稀有块在群里扩散开，保证整个群的“生态平衡”。
5. Tit-for-Tat（针锋相对 / 一报还一报）：这是 BT 的“激励机制”——你上传给我，我才上传给你。每个人会优先把带宽分给那些“上传速度快”的邻居（叫“疏通”unchoking）。上传越快，越受待见，下载自然也越快。这套“利人即利己”的规则，把“搭便车（只下载不上传）”的白嫖党逼得无路可走。

### 打个比方：一群人凑钱买一本限量书，谁复印得快、分享给别人多，谁就能更快地从别人那儿拿到自己缺的章节；只想着白嫖、一页都不肯复印的人，很快就会被踢出这个“互帮互助圈”。BitTorrent 正是靠“最稀缺优先”保生态、“针锋相对”防白嫖，才把 P2P 分发做成了教科书级的案例。
