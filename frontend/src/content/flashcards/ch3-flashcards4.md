# <span style="color: rgb(var(--brand));">可靠传输原理</span>

### 前面说过，网络层是“尽力而为”的——它会丢包、会出错、会乱序。可我们的应用却想要“可靠”：发出的数据必须一个不差、一个不乱地到达。怎么在一个“不可靠”的地基上盖出“可靠”的楼？这就是本节要解决的灵魂问题，也是 TCP 一切机制的底层思想。

# <span style="color: rgb(var(--brand-dark));"> 3.4.1 从完美信道出发：rdt1.0 </span>

### 我们一步步来。先假设一个“童话世界”：信道**不丢包、不出错、不乱序**。这时候发送方只要干一件事——把数据发出去；接收方只要干一件事——把数据收下来。这个最朴素的版本叫 `rdt1.0`，没有 ACK、没有重传，因为根本用不上。

# <span style="color: rgb(var(--brand-dark));"> 3.4.2 信道会出错：rdt2.0 → rdt2.2 </span>

### 现实没那么美好，第一步先加入“`比特可能出错`”。于是就有了两种反馈：

> `ACK（肯定确认）：收到了，而且没出错，请继续发下一个。`
> `NAK（否定确认）：收到了，但出错了，请重发。`
### 在计算机网络的环境中，基于这样的重传机制的可靠数据传输协议称为`自动重传请求（Automatic Repeat reQuest，ARQ）`协议.
### 这就是 `rdt2.0`。但它有个致命的 bug：万一 *ACK/NAK 本身在传输中也出错了* 怎么办😵‍💫？就好比你一直问为什么，最后问出个为什么为什么的问题一样（有点形而上学的意味）。发送方会懵圈。解决办法是给数据包`编上序号（sequence number）`：

* `rdt2.1`：用序号 0/1 交替，发送方通过序号判断对方确认的是哪一个包。
* `rdt2.2`：干脆去掉 NAK，只保留 ACK + 序号——收到重复的 ACK 就知道“上个包出错了，要重发”。

# <span style="color: rgb(var(--brand-dark));"> 3.4.3 信道还会丢包：rdt3.0 </span>

### 再现实一点：包可能`整个丢失`（连 ACK 都等不到）。于是引入`超时重传`——发送方每发一个包就启动一个定时器，超时还没收到 ACK 就重发。这就是 `rdt3.0`，也就是“`停止-等待协议`”：发一个、等确认、再发下一个。

### 它的缺点一目了然：发一个包要干等一个 RTT（往返时延），效率低得可怜。于是有了`流水线（pipelining）`——一口气连续发多个包不等确认。流水线又分两种：

* `回退 N 步（Go-Back-N, GBN）`：允许发送方最多有 N 个未确认的包；一旦某个包出错，从它开始**全部重传**。
* `选择重传（Selective Repeat, SR）`：接收方单独确认每个包，只重传真正出错/丢失的那几个。

# <span style="color: rgb(var(--brand-dark));"> 3.4.4 小结 </span>

### 可靠数据传输的“三板斧”其实就这三样，后面学 TCP 会反复见到它们：

1. `确认（ACK）`：让发送方知道“到没到、错没错”。
2. `序号（seq）`：区分不同的包，识别重复与乱序。
3. `超时重传（timeout）`：兜底，收不到确认就重发。

### 把这三样组合得聪明一点，就能在不可靠的信道上实现可靠传输——这就是 TCP 的底气所在。下一节就来认识认识这个“未见其面，先闻其声”的TCP。
