# <span style="color: rgb(var(--brand));">拥塞控制原理</span>

### 前面的流量控制是“别把接收方淹死”，这一节的拥塞控制是“别把整个网络淹死”。想象一下早高峰的路口：每辆车都只顾自己冲，结果谁都走不动。拥塞的本质就是——**太多源、太快地把数据灌进网络，而中间路由器的缓冲和处理能力有限**。

# <span style="color: rgb(var(--brand-dark));"> 3.6.1 拥塞的成因与代价 </span>

### 先看一个经典的简化场景：两个发送方、一个共享路由器、有限缓冲。当发送速率逼近链路容量时，会发生这些连锁反应：

1. 排队时延暴涨：分组在路由器里排队，越来越慢。
2. 丢包：缓冲满了，新来的分组被无情丢弃。
3. 带宽被浪费：那些好不容易传到一半、却在路上被丢弃的分组，白白消耗了上游链路的带宽。

### 更要命的是死循环：发送方发现超时丢包 → 于是重传 → 网络更堵 → 又丢 → 再重传……拥堵雪上加霜。这就是拥塞的代价：**时延变长、吞吐下降、资源白费**。

# <span style="color: rgb(var(--brand-dark));"> 3.6.2 两种拥塞控制思路 </span>

### 怎么解决拥塞？业界有两条路：

* 端到端的拥塞控制（end-to-end）：网络层啥也不说，端系统自己从“丢包/时延”这些现象里猜网络堵不堵。TCP 走的就是这条路——它没有网络层的直接帮助，只能靠观察 ACK 和超时来判断。
* 网络辅助的拥塞控制（network-assisted）：路由器/交换机主动告诉端系统“这里堵了，慢点”，甚至直接按速率分配资源（比如 ATM 的 ABR 服务）。

### 因特网现实选择了端到端（因为改动路由器太难、代价太高），这也注定了 TCP 只能“摸着石头过河”——而它怎么摸，就是下一节的主角。

# <span style="color: rgb(var(--brand-dark));"> 3.6.3 一个小结 </span>

### 记住这条主线：

* 拥塞 = 网络资源（链路带宽、路由器缓冲）供不应求。
* 代价 = 时延↑、丢包↑、有效吞吐↓。
* 目标 = 在不打垮网络的前提下，让每个连接都尽可能高效、公平地分享带宽。

### 而 TCP 实现这个目标的方法——慢启动、拥塞避免、快重传——马上揭晓。
