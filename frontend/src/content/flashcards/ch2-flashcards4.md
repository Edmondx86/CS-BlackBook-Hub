# <span style="color: rgb(var(--brand));">域名系统 (DNS)</span>

### 上一张卡埋了个钩子：你敲下的 `www.baidu.com` 到底是怎么变成一串数字 IP 地址的？现在就来揭晓。人类记名字（`baidu.com`），机器认数字（`180.101.50.188`），中间需要一座“翻译桥”——这就是 **DNS（Domain Name System，域名系统）**。它就像网络世界的“黄页电话本”，你报名字，它给你号码。

# <span style="color: rgb(var(--brand-dark));"> 2.5 DNS 概述：因特网的电话簿 </span>

### DNS 是由`分层的 DNS 服务器`实现的**分布式数据库**，外加一个让主机能够查询这个数据库的**应用层协议**。别小看它，它的活儿可不只是“域名换 IP”这么简单，具体提供四类服务：

1. **主机名 → IP 地址的翻译**：把你输入的 `www.xxx.com` 翻译成机器能识别的 IP 地址，这是它最核心的本职工作。
2. **主机别名（host aliasing）**：一个主机可能有个又长又绕的“正名”（canonical hostname），比如 `relay1.west-coast.enterprise.com`，但它同时还有个好记的“别名”`www.enterprise.com`。DNS 能帮这个别名也翻译出来。
3. **邮件服务器别名**：就像网站有 `www` 一样，邮件服务器也有别名，方便用户记忆。
4. **负载均衡（load distribution）**：像百度、淘宝这种超热门网站，同一个域名背后其实绑着一堆服务器。DNS 会在这堆 IP 地址里“轮流转”着返回，把流量均匀摊开，防止全挤到一台机器上。

### 但要先说清一个“天大的误会”：DNS 并不是坐在用户和服务器之间转发数据的那条“传输带”，它只负责“指路”。它跑在 **UDP** 之上，默认端口是 `53`——因为“翻译个名字”这种小事，不值得像 TCP 那样先握手半天。

## <span style="color: rgb(var(--brand-dark));"> 2.5.1 DNS 的层次树状结构 </span>

### 全球这么多域名，如果都塞进一个巨大的“总账本”，那这台服务器早就被查询请求冲垮了。所以 DNS 采用了“分而治之”的`层次化（hierarchical）`设计，从上到下分成四级：

1. **根 DNS 服务器（root DNS servers）**：金字塔尖，全球只有 13 台（其实是 13 组，背后还有上百台镜像撑着）。它不直接存“名字→IP”的答案，而是告诉你“去问哪个顶级域”。
2. **顶级域 DNS 服务器（Top-Level Domain, TLD）**：负责 `.com`、`.org`、`.net`、`.edu`、`.cn` 这些顶级域，以及 `.uk`、`.jp` 这类国家域。你问 `baidu.com`，`.com` 服务器会告诉你“去问 baidu.com 的权威服务器”。
3. **权威 DNS 服务器（authoritative DNS servers）**：真正的“房主”。每个组织（大学、公司）在自己可公开访问的主机上维护自己域名的记录，最终答案就出自这里。
4. **本地 DNS 服务器（local DNS server）**：严格来说它不属于这四级，但它是“接线员”——你电脑每次发起的 DNS 请求，第一个找的都是它（通常由你的 ISP 提供）。

## <span style="color: rgb(var(--brand-dark));"> 2.5.2 递归查询与迭代查询 </span>

### 现在来看看一次完整查询是怎么“跑”起来的。假设你在浏览器输入 `www.baidu.com`：

1. 你的电脑先问**本地 DNS 服务器**：“帮我查一下 `www.baidu.com` 的 IP。”
2. 本地 DNS 服务器去问**根服务器**，根服务器说：“`.com` 的我不管，你去找 .com 的 TLD 服务器。”（顺手把 TLD 地址甩给它）
3. 本地 DNS 服务器又跑去问 **`.com` TLD 服务器**，TLD 说：“`baidu.com` 我这儿也没有具体答案，你去找它的权威服务器。”
4. 本地 DNS 服务器再跑到**权威服务器**，这次终于拿到了 `www.baidu.com` 的真实 IP。
5. 本地 DNS 服务器把答案带回给你，你的电脑就能连上去了。

### 这里涉及两种查询方式：`递归查询（recursive query）`是“你只问一个人，剩下的他全帮你跑腿”，就像点外卖，你跟老板说“给我送到家”，具体怎么送不用你管；`迭代查询（iterative query）`则是“你自己一个个去问，别人只告诉你下一站去哪”，就像问路，A 说“往前走 100 米左转”，你得自己再问 B。

## <span style="color: rgb(var(--brand-dark));"> 2.5.3 DNS 记录与缓存 </span>

### DNS 服务器存的那些“答案”长什么样？它们都是`资源记录（Resource Record, RR）`，每条由四元组构成：`(Name, Value, Type, TTL)`，其中 Type 决定了“这条记录怎么读”：

1. **Type = A**：Name 是主机名，Value 是对应的 IP 地址。这是最经典的“名字→号码”。
2. **Type = CNAME**：Name 是别名，Value 是它的“正名”（canonical name）。有了它，别名才能顺利指到正主。
3. **Type = NS**：Name 是某个域（如 `baidu.com`），Value 是它的权威服务器的名字，相当于“这块地皮归谁管”。
4. **Type = MX**：Name 是域名，Value 是它的邮件服务器名字。想让 `xxx@baidu.com` 送到正确的地方，靠的就是它。

### 最后说说**DNS 缓存**。如果每次查 `www.baidu.com` 都要从根服务器一路问到权威服务器，那根服务器早就“冒烟”了。所以本地 DNS 服务器会把查到的结果缓存一段时间（由 TTL 控制），下次再有人问同样的问题，直接从缓存里掏答案，既快又给上游减负。当然，缓存也有“翻车”的时候——域名的 IP 变了，缓存里还是旧地址，你就可能连到一台已经“搬走”的服务器。这时要么等 TTL 过期，要么手动 `ipconfig /flushdns` 清缓存（Windows 用户应该都干过这事）。

### DNS 这块“电话簿”就翻完了：层次结构负责“分工”，递归/迭代负责“查”，缓存负责“提速”。有了它，你才能舒舒服服敲域名，而不是背一串 IP。下一张卡，我们把目光转向比 Web 更“老资格”的应用——电子邮件，看看一封信是怎么跨过半个地球送到对方邮箱里的。
