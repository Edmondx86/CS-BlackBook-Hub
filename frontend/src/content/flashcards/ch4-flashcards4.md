# <span style="color: rgb(var(--brand));">泛化转发和SDN</span>

### 恭喜你一路杀到了第四章的最后一张卡片！在前面三张里，我们讲的转发全都是“看一眼目的 IP，查表，走人”——教科书般规矩的`基于目的地的转发（destination-based forwarding）`。可现实中的网络设备早就没这么“单纯”了：它们还得当防火墙、做 NAT、当负载均衡器、改报文头、给流量打标签……要是每加一个功能就得重新设计一种专用设备，工程师怕是要集体辞职。于是有人拍脑袋提出了一个相当霸道的想法：既然转发本质上就是**匹配某些字段** + **执行某些动作**，那干脆把匹配的字段放开、把动作也放开——这就是`泛化转发（generalized forwarding）`。

### 还记得 4.1.1 里埋的那个伏笔吗？当时说`现在控制平面采用的都是 SDN 方法`，一句话带过就跑了。现在终于到了还债的时候：泛化转发里那张神通广大的`流表`，到底是谁算出来的？答案是`软件定义网络（Software-Defined Networking，SDN）`——一个逻辑集中的控制器，把全网的流表算好，再挨个下发给底下的交换机。

### 先记住一句话：**一个流表项 = 匹配 + 动作 + 计数器**。匹配决定“哪些分组归我管”，动作决定“这些分组怎么处理”，计数器负责“数一数到底处理了多少个分组、多少字节”。传统路由器只匹配目的 IP，也只会“转发到某个端口”；而泛化转发把这两件事同时解锁了，于是路由器、交换机、防火墙、NAT、负载均衡器……突然都能用同一套抽象来描述，一台设备也能身兼数职，这套“匹配加动作（match-plus-action）”的机制就是它“泛化”的地方。

# <span style="color: rgb(var(--brand-dark));">4.4.1 匹配（Match）</span>

### 匹配的字段可以跨层，从链路层一路捅到运输层。以 OpenFlow 1.0 为例，它能匹配的“钥匙孔”有十多个，大致分三档：

* **链路层**：入端口、源 / 目的 MAC 地址、以太网类型、VLAN ID、VLAN 优先级。
* **网络层**：源 / 目的 IP 地址、IP 协议号（TCP？UDP？ICMP？）、IP 服务类型（ToS）。
* **运输层**：源 / 目的端口号。

### 注意，这里没有最长前缀匹配的浪漫（💀死去的 4.2.1 记忆又开始攻击我）：字段的值可以带上`通配符（wildcard）`，也就是`这一位我不关心`。比如一条流表项写着`目的 IP = 10.0.0.\*`，那整个 10.0.0.0/24 的分组它都管。此外，流表项还可以带**优先级**，当多条表项同时匹配时，先按优先级高的来——毕竟“到底谁说了算”这件事，在哪儿都是个问题。

# <span style="color: rgb(var(--brand-dark));">4.4.2 动作（Action）</span>

### 匹配上了之后能干些什么？花样可比传统路由器多得多，归纳起来大致三类：

* **转发（Forwarding）**：把分组送到某个指定端口；也可以**广播**（所有端口）、**多播**（某些端口），或者干脆**上交给远程控制器**（让控制器自己看着办，比如它想先学一学这条流长什么样）。
* **丢弃（Dropping）**：直接扔掉，一个字节都不留。这不就是防火墙嘛——匹配到不该来的流量，反手就是一个丢弃。
* **修改字段（Modify）**：改写首部字段，比如把源 IP 换成公网地址、把端口重写一下（NAT 和负载均衡器就是这么干的），或者压入 / 弹出 VLAN、MPLS 标签（还记得 4.3.5 讲的隧道封装吗，思路是一回事）。

### 你可能会问：这些动作能叠加吗？当然可以。一条流表项完全可以“先把源 IP 改了，再从 3 号口发出去”，动作按顺序依次执行，这可比只能“查表转发”的传统路由器灵活太多了。

# <span style="color: rgb(var(--brand-dark));">4.4.3 OpenFlow 中的匹配加动作示例</span>

### 光讲概念太虚，来看三个经典场景，感受一下一条流表项到底能干多少活：

1. **简单转发**：匹配“目的 IP = 10.0.0.1”，动作“从端口 3 转发”。这就是最朴素的转发，和传统路由器干的活没区别。
2. **负载均衡**：匹配“目的 IP = 某台对外服务器 且 目的端口 = 80”，动作“把目的 IP 改写成 10.0.0.7、从端口 4 转发”。于是外面看起来只有一台服务器，实际上流量被悄悄分给了好几台后端。
3. **防火墙**：匹配“IP 协议号 = 6（TCP）且 目的端口 = 22”，动作“丢弃”。恭喜，SSH 被一刀切了，从此运维只能另想办法进来。

### 看出来了吗？同样一套“匹配 + 动作”，换几行流表就能从路由器变成防火墙，再变成负载均衡器。设备还是那台设备，功能全由表说了算，这就是“软件定义”四个字的底气。

# <span style="color: rgb(var(--brand-dark));">4.4.4 SDN：控制平面搬了个家</span>

### 那么问题来了：这些流表是谁填的？传统路由器里，路由选择算法和转发表都长在设备内部，每台设备各自为政（即`每路由器控制`）。SDN 的做法则相当粗暴——**把控制平面整个从设备里薅出来**，放到一个逻辑集中的远程控制器上：控制器掌握全网视图、算出流表，再通过`OpenFlow` 协议下发给每一台交换机。交换机自己只剩下傻乎乎的`数据平面`：按表办事，不多问一句。

### 所以 SDN 的三个关键字是：**流表**（转发的依据）、**控制与数据分离**（算表的和转发的分开）、**可编程**（写个程序就能定义网络行为）。至于控制器具体长什么样、南向 / 北向接口怎么分工，第五章还会专门讲，这里先混个脸熟就好。

# <span style="color: rgb(var(--brand-dark));">4.5 顺带一提：中间盒（Middleboxes）</span>

### 世界上除了路由器和交换机，还蹲着一大堆*不务正业*的设备：NAT、防火墙、负载均衡器、入侵检测系统、缓存代理……它们既不纯粹转发，也不纯粹路由，统称为`中间盒（middlebox）`。而它们干的活，恰恰就是“匹配 + 修改 / 丢弃”，所以用泛化转发的流表来统一描述再合适不过——这也正是 SDN 想要的：让网络功能从`专用硬件`变成`一段可编程的逻辑`。

### 当然，中间盒也不是没有争议：它插手了运输层端口、打破了端到端原则、让网络变得不那么“透明”（这些槽点在 4.3.4 讲 NAT 时我们已经吐槽过一轮了）。但现实就是，好用才是硬道理，它们至今活得很好。
